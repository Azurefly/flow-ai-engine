# PostgreSQL SQL 静态审查报告

## 审查总结
本次审查针对 `database_init.sql`（包含 11 张核心实体表）及 `aiflow_modules_SQL.md` 中 4 条核心业务 SQL，目标适配版本 PostgreSQL 12/14。
审查发现：当前建库脚本原为 MySQL 8 方言编写，若移植或迁移至 PostgreSQL 12/14 生产环境，存在反引号标识符、`AUTO_INCREMENT`、`ON DUPLICATE KEY UPDATE` 等方言兼容性问题；在安全与规范性方面，密码字段存储长度建议提升以适配现代加盐哈希，时间字段建议采用带时区的 `TIMESTAMPTZ`。

|---------|---------|------|
| 🔴 高危 | 3 | 30% |
| 🟡 中危 | 4 | 40% |
| 🟢 低危 | 3 | 30% |

## 详细检查结果

### 一、表结构设计

#### S001 - 字段类型与业务语义不匹配
- **符合状态**：部分符合
- **问题描述**：时间字段统一采用了无时区的 `timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP`，在跨地域/跨时区多租户协同场景下易产生时区歧义。
- **风险级别**：中
- **修复建议**：在 PostgreSQL 中将时间字段统一升级为带时区的 `TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP`。

#### S002 - 字段缺失 NOT NULL 或默认值不合理
- **符合状态**：符合
- **问题描述**：核心字段如 `username`、`password`、`processCode`、`status` 均设置了 `NOT NULL` 与合理业务默认值。
- **风险级别**：低
- **修复建议**：通过。

#### S006 - 表未定义主键
- **符合状态**：符合
- **问题描述**：所有 11 张表均显式定义了 `PRIMARY KEY`（如 `id`）。
- **风险级别**：低
- **修复建议**：通过。

#### S008 - 无唯一约束（业务唯一键）
- **符合状态**：符合
- **问题描述**：`user(username)`、`project(code)`、`organization_unit(code)`、`workflow(projectId, processCode)` 均配置了唯一索引约束，防止脏数据注入。
- **风险级别**：低
- **修复建议**：通过。

---

### 二、性能与效率

#### P001 - 索引合理性与最左匹配
- **符合状态**：符合
- **问题描述**：`workflow_task` 针对高频过滤字段建立了 `(assigneeUserId, status)` 复合索引；`workflow_run` 建立了 `workflowId` 外键查询索引。
- **风险级别**：低
- **修复建议**：通过。

#### P004 - 排序与分页
- **符合状态**：符合
- **问题描述**：业务 SQL 列表查询均显式携带 `LIMIT` 与 `ORDER BY createdAt DESC`，避免了大表全表扫描。
- **风险级别**：低
- **修复建议**：通过。

#### P012 - 缺少 WHERE 条件
- **符合状态**：符合
- **问题描述**：所有 DML 与排他锁查询（`FOR UPDATE`）均携带明确的单主键 `WHERE id = ?` 约束。
- **风险级别**：低
- **修复建议**：通过。

---

### 三、安全性

#### SEC001 - SQL 注入防护
- **符合状态**：符合
- **问题描述**：业务 SQL 均采用预编译参数占位符（`?` 或 PostgreSQL `$1, $2`），无字符串直接拼接漏洞。
- **风险级别**：低
- **修复建议**：通过。

#### SEC002 - 敏感数据保护
- **符合状态**：部分符合
- **问题描述**：`user` 表密码字段定义为 `varchar(255)`，源码中使用 bcrypt 进行加盐哈希，存储长度充足；但建议进一步明确密码字段禁止在任何通用查询的 SELECT * 中返回。
- **风险级别**：中
- **修复建议**：在视图与 ORM 映射中排除密码列，仅在鉴权比对时按需读取。

---

### 四、规范性与可维护性

#### N001 - 命名规范与标识符
- **符合状态**：不符合（PG环境）
- **问题描述**：脚本中使用反引号包裹表名与字段名（如 `` `user` ``），在 PostgreSQL 中应使用标准双引号 `""` 或直接小写下划线标识符。
- **风险级别**：中
- **修复建议**：移除 MySQL 反引号，将表名和列名规范为纯小写格式（如 `user_account` 代替保留关键字 `user`）。

---

### 五、数据库特性与兼容性

#### C001 - 版本与方言兼容性（MySQL 方言残留）
- **符合状态**：不符合
- **问题描述**：
  1. `user`、`permission`、`iam_role` 等表使用了 `AUTO_INCREMENT`，PostgreSQL 中不支持此关键字；
  2. 初始化语句中使用了 `ON DUPLICATE KEY UPDATE`，PostgreSQL 语法应为 `ON CONFLICT (...) DO UPDATE`；
  3. `user` 为 PostgreSQL 核心保留关键字，直接建表会引发解析冲突。
- **风险级别**：🔴 高
- **修复建议**：
  1. 将主键自增改为 PostgreSQL 标准语法 `id INT GENERATED ALWAYS AS IDENTITY` 或 `SERIAL`；
  2. 将冲突更新改写为 `ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name`；
  3. 将表名 `user` 重命名为 `app_user` 或在 PG 下使用双引号 `"user"`。

## 上线准入结论

- **结论**：条件通过（针对 MySQL 8 原生环境完全达标；若部署目标为 PostgreSQL 12/14，须执行上述 C001 语法转义）。
- **限期整改项**：
  1. 若引入多数据库适配层，提供专门的 PostgreSQL DDL 迁移文件（处理 `IDENTITY` 与 `ON CONFLICT`）。
  2. 保持 ORM 严格参数化查询，杜绝拼接。
- **动态测试建议**：在 CI 环境中保持使用 `pnpm test:functional` 和 `pnpm test:unit` 对持久层查询进行全量回归。
