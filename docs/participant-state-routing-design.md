# 参与人状态流设计与验收

日期 2026-11-16

## 运行合同

流程定义通过 `settings.stateModel = "participant-v1"` 显式选择参与人状态模式，选择随版本发布和运行快照固定。未设置此字段的流程使用既有执行路径。每个新模式实例每人一张状态卡，使用既有参与人状态表的 `default` 角色槽，身份和 IAM 角色参与条件匹配。

状态节点表示驻留状态。状态到操作的连线授予该卡持有人一个可办理任务。操作提交后沿所选结果出口经过路由，为受影响人员计算目标状态，遇到状态即停止自动执行。多个受影响人员可以命中不同出口。每人每次只落入一个目标状态，缺少匹配时可由路由选择保持原状态。路由内部回路必须在发布时拒绝，跨越人工操作的业务返回允许重复执行。

路由复用现有角色、条件、优先级和目标连线配置。被评估人员上下文为 `participant`，包括 userId、stateCode、stateName、isActor、isReceiver、isRelationSender、isRelationReceiver。`action` 包括本次操作人、接收人和结果。所有人使用同一份操作前状态快照，计算顺序不会改变匹配结果。同优先级且同时命中多个目标属于冲突，整次操作失败。

## 操作影响范围和关系

操作节点的 `participantOperation` 配置描述本次影响范围以及关系处理方式。

- `scope` 可选择 actor、actor_and_receivers、relation、all，分别覆盖操作人、操作人与新接收人、本轮关系人员、实例全部已有人员。
- `relation` 可选择 none、create、consume。create 根据节点现有人员配置解析接收人并生成新的提交关系。consume 使用操作人卡片当前绑定的活动关系，并关闭该关系。新的关系有独立标识，保存发送人和接收人。
- 需要新接收人的操作复用指定用户、角色、部门、主管和表单用户解析器。操作办理人始终由持卡人确定。
- 关闭关系后，所有绑定该关系的待办重新核对资格。仅允许 consume 的操作在活动关系存在时开放。卡片变更会取消该卡的旧待办并创建新版本待办。
- create 遇到仍被其他活动关系占用的接收人时拒绝，要求设计者先通过操作关闭原关系，防止一人一卡被不同提交覆盖。

提交操作可设为 create，将 A 路由到已提交、B 路由到待处理。撤回和处理可设为 consume，分别由持卡人执行。撤回将 A 路由到已撤回待提交、B 路由到下级已撤回。再次提交生成新关系和新待办。

## 一致性和历史

所有操作先锁定运行实例，再锁定和校验任务、持卡版本、当前关系和有效用户。在同一数据库事务中完成任务决策、关系关闭或创建、个人状态变更、旧任务及提醒失效、新任务、节点历史、状态迁移事实和运行版本更新。A 撤回与 B 处理竞争同一个运行锁，成功的一方使另一方旧任务失效。失败回滚整个事务。

使用 `workflow_run.contextJson.runtime.participantState` 保存版本化运行数据，使用既有参与人状态表投影卡片，使用 `workflow_state_transition.payloadJson` 保存每次操作的逐人前后状态及关系信息。复用现有表结构，无需改写历史数据。既有任务唯一键中的 executionKey 绑定卡片版本，旧任务不能用于新轮次。已成功任务重试可返回对应已提交结果，不能重复推进。

实例整体显示办理中或已完成。只有全部已存在卡片进入个人终态时实例才完成。个人终态仍可在实例办理期间被新的合法操作选中。全部卡片均无可执行操作且未满足完成条件时，拒绝产生不可继续的结果。

新模式的原子路径支持开始、操作、路由、状态和结束节点。HTTP、子流程等异步副作用需要独立的事务后执行合同，发布校验会明确指出这些节点尚未纳入此模式。任务领取、办理、表单、待办列表和历史复用现有入口。参与人身份变化应在图中配置，新模式禁止直接移交或代理持卡操作。

## 设计器与工作台

状态流程画布提供模式选择。参与人模式显示操作影响范围和关系配置，路由提供人员上下文引用和未命中行为，状态显示可执行操作连线的含义。提供提交、撤回、处理的可编辑示例图。工作台复用操作任务表单和按钮，实例详情展示每个人的当前状态以及每次操作的批量变化。

## 验收要求

- 旧状态流、控制流、数据流编译与运行回归保持通过。
- 新模式正常保存、审核、发布、预检、启动及多身份办理。
- A 提交后双方拥有正确状态与操作，撤回后 B 已打开的旧待办提交失败。
- 再提交可更换接收人，新旧关系和任务历史可区分。
- A 撤回与 B 处理并发仅一个成功，状态和任务一致。
- 重复提交幂等，事务中断整体回滚，启动任务重试不重复创建卡片。
- 无权限账号、停用账号、伪造任务、已结束任务不能操作。
- 路由角色匹配、逐人条件、优先级、冲突、默认保持、状态终结有自动化覆盖。
- 发布后修改草稿不改变已运行实例语义。
- 本地真实 MySQL、浏览器及部署后隔离验收分别记录结果。

## 2026-11-18 组合路由扩展

分支支持流程发起人、全部受影响参与人、当前操作人、接收人、提交关系人员、指定用户、IAM 角色、当前个人状态和业务数据。条件组可嵌套选择全部满足、任一满足，每条条件及条件组均可取反。人员条件与原分支条件共同匹配，使用原优先级和默认分支规则。

部门条件支持多个部门、任一所属部门或仅主部门，以及包含本部门的第 0 层、直属子部门第 1 层和指定起止层级。最深层级为空表示全部下级。组织层级在办理事务内读取，停用部门不可作为有效筛选根节点，部门循环会拒绝执行。

操作结果按人员、操作节点和提交关系轮次保存。`participant.results` 读取当前被评估人员本轮结果，`participants.人员ID.results.操作节点ID.字段` 读取本轮指定人员结果。重新提交生成新关系后，旧轮次结果不参与匹配。组合这些结果可配置人数门槛、顺序会签和多路审核汇合。同一人可持有多个可执行操作，其他人员提交意见而未改变该人的状态时，其待办和截止时间保持稳定。

角色和接收人解析复用办理事务连接，避免满载连接池中的嵌套借用等待。任务取消和个人状态投影使用具体记录主键更新，降低并发实例之间的间隙锁竞争。

本轮类型检查、生产构建、2525 项单元测试、71 项功能测试、13 项场景测试及 12 项真实 MySQL 测试通过。数据库测试包含 24 个不同实例同时办理。前端构建总量 1618.69 KiB、gzip 497.76 KiB，预算调整为 1620 KiB 和 499 KiB，单块预算仍为 450 KiB。


## 并发运行优化（2026-11-18）

后台状态／控制与数据流通道默认各并发处理 4 个作业，可通过 `WORKFLOW_WORKER_CONCURRENCY` 调整到 1–8。处理完有工作的一批后立即继续领取，空闲时仍按既有轮询周期检查。状态／控制作业依次领取租约后并行执行，避免领取范围锁相互竞争；批次中发生错误也等待其他租约持有者完成后才释放通道，停机仍等待在途工作。

发起运行仅共享锁定业务、发布定义及数据流调用者身份，避免相同业务的独立实例彼此串行和外键锁升级死锁。修改定义、归档和账号变更仍需排他锁，权限在事务内重新检查。真实 MySQL 回归确认两次准入可同时持有共享业务锁，但归档写锁不能越过未提交的准入。

性能验收分别记录接口响应、实例进入待办／完成的时间、办理响应和错误率；异步接口快速返回不等于后台已完成。远程测量结果另见并发验收报告。


远程并发测试进一步确认，队列领取的状态索引在默认隔离级别下出现间隙锁交叉等待。状态／控制和数据流仅在领取租约的下一笔事务使用 `READ COMMITTED`，保留 `FOR UPDATE SKIP LOCKED` 和租约校验；不更改连接池会话默认隔离级别或业务办理事务。真实 MySQL 以 8 个消费者竞争 32 个作业验证无死锁、无重复执行和每个作业仅领取一次。隔离行为参考 [MySQL 8.4 事务隔离说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。


真实提案并发进一步覆盖了人工任务提醒。提醒候选先不加锁读取，再依次锁定实例、任务、提醒；遇到正在办理的实例使用 `SKIP LOCKED` 留待下轮处理，事务内再次检查是否到期和任务是否有效。取消旧提醒不再使用反向持锁的多表更新。后台连续处理积压任务时，计时、恢复等维护扫描仍按原轮询间隔执行，避免每一批作业重复扫描历史运行。
