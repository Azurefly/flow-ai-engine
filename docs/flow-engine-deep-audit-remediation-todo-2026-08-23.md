## 2. 总体结论

当前系统已经具备流程建模、版本发布、流程运行、人工任务、基础人员解析、项目/流程权限和运行日志等骨架，适合产品演示或边界明确的内部试点；尚不适合作为通用生产流程引擎承载关键审批、长事务流程或高可靠自动化。

最核心的差距不是“再增加几个节点”，而是以下生产语义尚未闭合：

1. 流程定义未经过完整图编译，非法图仍可能发布或以“成功”结束。
2. 执行主要绑定 API 请求进程，缺少持久化调度、租约、重试、幂等和崩溃恢复。
3. 审批结果被固定成通过，或签/会签只实现了正向完成票数，没有拒绝、否决、驳回路径等关键语义。
4. LLM 节点有调用代码，但当前部署未配置密钥，画布连接矩阵也使其在常见流程中难以连入，不能称为可用。
5. 数据流目前是样例执行器，数据源创建时未经真实连接测试却可被标为已验证。
6. TLS、登录防护、就绪探针、不可变审计、备份恢复和构建身份等生产门禁不完整。
7. 前端桌面端基本可操作，但设计器信息密度过高；375px 下存在页面级横向溢出和关键操作区域超宽。

## 6. 详细问题与改造方案

### 6.1 流程定义与执行内核

#### COR-001（P0）流程图没有经过生产级编译校验

- **现状证据**：[`server/workflow-service.ts`](../server/workflow-service.ts#L14) 主要检查 JSON 格式、单一起点/终点、节点 ID 唯一、边端点存在和起点出边；对应测试 [`server/workflow-definition-validation.test.ts`](../server/workflow-definition-validation.test.ts#L4) 覆盖面很窄。
- **风险**：不可达节点、无法到达终点的分支、自环/非法环、重复边、无出口节点、错误 Handle、并行汇聚不闭合等定义可能进入发布态，运行后出现静默成功、重复执行或永久挂起。
- **改造方案**：新增独立 `WorkflowCompiler`，把设计态 JSON 编译为规范化、版本固定的执行计划；校验节点/边唯一性、起终点、全图可达性、每个可执行分支可达终点、循环策略、分支默认路由、并行/汇聚配对、端口兼容和节点配置 Schema。编译错误必须包含节点 ID、路径、错误码和可定位提示。
- **验收标准**：至少建立 25 类合法/非法图用例；任一非法图不能发布；合法图编译结果顺序稳定且可做哈希；前端在节点和问题面板同时定位错误。
- **依赖**：无；是 COR-002、COR-004 和子流程改造的前置条件。

#### COR-002（P0）运行成功条件不等于业务成功

- **现状证据**：[`server/workflow-engine.ts`](../server/workflow-engine.ts#L582) 使用进程内 `executed Set` 跳过重复节点；队列耗尽后可返回成功和空输出，没有把“已到达有效终点”作为成功必要条件。
- **风险**：条件无匹配、死路、错误连线或重复节点被跳过时，运行可能显示成功，但业务事实上没有完成。
- **改造方案**：运行状态机只允许在至少一个合法终点按定义策略完成后进入 `succeeded`；区分 `failed`、`blocked`、`waiting`、`cancelled`、`terminated` 和 `compensating`。保存终点到达事件、最终输出和结束原因。
- **验收标准**：无匹配路由、走入死路、节点异常、等待人工、取消和真正到达终点分别得到准确状态；任何 `succeeded` 均能关联终点节点运行记录。
- **依赖**：COR-001。

#### COR-003（P0）缺少持久化 Worker 与崩溃恢复

- **现状证据**：[`server/workflow-engine.ts`](../server/workflow-engine.ts#L395) 在请求路径中执行工作流；[`drizzle/schema.ts`](../drizzle/schema.ts#L289) 虽有 `executionLockToken`/`executionLockExpiresAt`，但当前没有形成完整的租约领取、续租、超时回收和恢复闭环。
- **风险**：API 进程重启、超时、部署或网络断开时，运行可能中断、重复调用外部系统或长期停留在错误状态。
- **改造方案**：引入持久化 job/step 表和独立 Worker；API 只写入启动命令与 Outbox。Worker 通过数据库原子领取租约，步骤执行使用幂等键，定期续租，失效后可安全回收；每次状态迁移与下一步入队同事务提交。
- **验收标准**：在节点执行前、执行中、提交后分别杀掉 Worker，重启后均能继续；外部副作用最多一次或通过幂等键等效一次；双 Worker 竞争不重复消费；人工任务可跨部署继续。
- **依赖**：COR-001、COR-002。

#### COR-004（P1）并行、汇聚、循环和重复到达语义不明确

- **现状证据**：当前 `executed Set` 把节点视为一次性执行，无法表达循环迭代、并行 Token 和汇聚等待条件。
- **风险**：复杂流程一旦出现并行或循环，实际执行与用户画布理解不一致。
- **改造方案**：采用 `run token + node instance + attempt` 模型；并行网关生成 Token，汇聚按实例/分支集合计数，循环必须配置最大次数、退出条件和超限动作。
- **验收标准**：并行 2/3/全部汇聚、重复到达、嵌套分支和受限循环均有确定性测试；同一汇聚只推进一次。
- **依赖**：COR-001、COR-003。

#### COR-005（P1）缺少运行控制和时间驱动能力

- **现状证据**：尚未形成暂停、恢复、取消、终止、定时器、消息订阅、催办、升级和补偿的统一命令模型。
- **风险**：长流程无法运维，人工任务无法满足 SLA，异常流程只能直接改库或删除。
- **改造方案**：建立幂等运行命令表；增加 Timer Job、消息关联键、SLA 策略和补偿步骤；运行控制必须校验权限并写审计。
- **验收标准**：暂停后不再领取新步骤；恢复不重复；取消/终止结果明确；服务停机跨过定时点后只补触发一次；催办与升级可追踪。
- **依赖**：COR-003、IAM-001、AUD-001。

### 6.2 审批、或签/会签与人员补充

#### APR-001（P0）审批决定被前端固定为通过

- **现状证据**：[`client/src/components/ProcessWorkbench.tsx`](../client/src/components/ProcessWorkbench.tsx#L264) 等处提交 `{ decision: "approved" }`；用户没有完成拒绝、退回、意见校验的真实操作链路。
- **风险**：界面上的“审批”实际等同于“同意”，关键业务无法拒绝，且审计数据失真。
- **改造方案**：后端定义权威 `ApprovalDecision` 枚举与状态机，例如 `approve/reject/return/abstain`；每种动作配置意见是否必填、可选退回目标和路由结果。前端只展示后端返回的当前可用动作，不能自行拼接决定。
- **验收标准**：同一任务可按配置提交通过或拒绝；重复提交返回幂等结果；无权限用户 403；决定、意见、操作者、代理关系、时间和目标节点完整持久化。
- **依赖**：COR-002。

#### APR-002（P0）或签/会签只计算完成数量

- **现状证据**：[`shared/reference-operate-config.ts`](../shared/reference-operate-config.ts#L150) 将或签阈值设为 1、会签阈值设为比例人数；[`server/workflow-engine.ts`](../server/workflow-engine.ts#L730) 主要统计 `status='completed'`，未按审批决定计算赞成/反对票。示例中的“汇报会签”还使用了 `orSignFor`，名称与配置不一致。
- **风险**：第一个拒绝者也可能被计作“完成”并推动流程通过；会签比例无法表达否决、全拒、弃权和剩余票数已不可能改变结果等规则。
- **改造方案**：把人员范围快照、通过阈值、拒绝阈值、否决规则、弃权规则、缺席处理、完成策略作为审批组配置；组状态由数据库事务内的票数聚合计算。支持并行会签，并将“顺序会签”作为独立模式。
- **验收标准**：覆盖一票通过、一票否决、全部同意、比例同意、全部拒绝才拒、顺序会签；并发最后两票只有一个请求推进流程；同一主体不能重复投票。
- **依赖**：APR-001、COR-003。

#### APR-003（P1）动态人员解析覆盖不足

- **现状证据**：[`server/organization-service.ts`](../server/organization-service.ts#L393) 可沿主部门向父级查找直属负责人；[`server/organization-service.ts`](../server/organization-service.ts#L459) 支持指定接收人、用户、发起人、发起人/发送人主管和角色，但自动关联模式范围有限。
- **风险**：常见的二级主管、部门负责人、岗位、项目负责人、表单选人、跨组织审批无法建模；空候选时可能阻断流程。
- **改造方案**：建立可扩展 `ParticipantResolver` 注册表；支持 N 级主管、指定组织负责人、岗位/职位、项目角色、表单字段、表达式和组合规则；提供设计态“按样例用户预览解析”及运行时解析解释。
- **验收标准**：每种解析器有成功、空结果、禁用用户、多部门、负责人本人和跨层级测试；结果中保存来源与解释链。
- **依赖**：组织数据契约稳定。

#### APR-004（P1）人员补充与代理机制未闭环

- **现状证据**：没有完整的加签、减签、转办、委托、休假代理及无人候选降级策略。
- **风险**：人员离岗或漏配时流程无法继续；临时变更只能管理员改数据，且责任归属不清。
- **改造方案**：分别定义“前加签/后加签/并行加签”“转办”“委托代理”“管理员改派”；限制谁可操作、何时可操作、是否保留原责任人、如何影响票数。配置空候选策略：失败、交给管理员队列、回退上级或指定兜底人，禁止静默跳过。
- **验收标准**：每个动作均有权限、并发和审计测试；代理提交同时记录实际操作者与责任主体；无人候选绝不被自动视为通过。
- **依赖**：APR-001、APR-002、AUD-001。

#### APR-005（P1）候选人快照与撤权语义未产品化

- **现状证据**：任务创建时会形成候选人快照，这是可保留能力；但角色解绑、账号禁用、部门变更后，已分配任务是否继续可办没有统一规则。
- **风险**：权限被撤销的用户仍可处理关键任务，或组织变更导致在途任务突然无人可办。
- **改造方案**：明确三层规则：候选范围是否快照、操作时是否二次校验账号状态、强制撤回/改派由谁执行。默认建议保留业务候选快照，但提交时必须校验账号启用、会话有效和未被显式撤销。
- **验收标准**：角色移除、账号禁用、成员离职和管理员强制改派均有确定行为与审计。
- **依赖**：IAM-001。

### 6.3 权限拦截与职责分离

#### IAM-001（P1）权限模型粒度不足

- **现状证据**：[`server/_core/trpc.ts`](../server/_core/trpc.ts#L13) 提供登录/管理员服务端中间件；[`server/iam-service.ts`](../server/iam-service.ts#L4) 主要定义流程创建、查看、编辑、发布、运行、成员管理和 IAM 管理；项目、任务与数据另有访问检查。这些基础拦截应保留。
- **风险**：无法分别授权查看运行、取消运行、重试节点、转办任务、导出数据、查看敏感输入、管理组织、读取审计等动作；缺少显式拒绝和职责分离。
- **改造方案**：使用统一 `authorize(subject, action, resource, context)`；补齐 `task:*`、`run:*`、`data:*`、`org:*`、`audit:*`、`secret:*` 等动作；支持项目/流程/实例范围、时效、显式拒绝优先和敏感字段策略。
- **验收标准**：所有 mutation 在服务端调用统一授权；前端隐藏按钮只作为体验；越权 API 测试覆盖匿名、普通成员、候选人、流程管理员、审计员和系统管理员。
- **依赖**：无。

#### IAM-002（P1）复核模式与自审约束未真正执行

- **现状证据**：[`server/p1-service.ts`](../server/p1-service.ts#L223) 保存 `reviewerMode`，但未在主要审批路径形成权威拦截；[`server/project-service.ts`](../server/project-service.ts#L140) 允许项目管理者执行审核，项目所有者可形成自审。
- **风险**：配置看似开启双人复核，实际仍可能由创建者、所有者或同一主体完成审批。
- **改造方案**：将职责分离作为后端策略：发起人与审批人不能相同、创建者与发布者不能相同、管理员代办需二次授权；冲突时不给候选资格或拒绝提交。
- **验收标准**：自审请求稳定 403；至少两种身份完成创建→复核→发布闭环；管理员紧急绕过需填写原因并产生高风险审计事件。
- **依赖**：IAM-001、AUD-001。

### 6.4 LLM、HTTP、数据流、表单和子流程节点

#### LLM-001（P0）部署环境下 LLM 节点不可用

- **现状证据**：[`server/_core/llm.ts`](../server/_core/llm.ts#L221) 在未配置密钥时抛错；[`compose.yaml`](../compose.yaml#L41) 未注入 LLM 配置。当前部署页面显示模型数为 0，控制台提示 `OPENAI_API_KEY is not configured`；前端查询失败后按空数组显示，容易被误解为“没有模型”。
- **风险**：用户能配置 LLM 节点但运行必失败，属于功能名存实亡。
- **改造方案**：增加 Provider 配置与启动/就绪校验；密钥通过 Docker Secret/外部 Secret Manager 注入，禁止进入流程定义和日志；模型查询失败展示明确错误与管理员配置入口。若无 Provider，则隐藏或禁用 LLM 节点并标注原因。
- **验收标准**：部署后 `/readyz` 能区分“核心服务就绪”和“LLM 能力未就绪”；真实模型完成一次确定输入的节点 E2E，保存模型、耗时、Token、费用估算、请求 ID 和脱敏错误。
- **依赖**：OPS-001。

#### LLM-002（P0）LLM 画布连线契约阻断常见路径

- **现状证据**：[`client/src/components/WorkflowCanvas.tsx`](../client/src/components/WorkflowCanvas.tsx#L34) 的目标类型矩阵没有让常见状态/控制节点把 LLM 作为目标；LLM 图标存在，但常规流程中难以连入。
- **风险**：即使后端配置有效，用户也无法设计可执行的 LLM 流程。
- **改造方案**：以共享节点端口契约作为前后端单一真源，定义控制流输入/输出与数据输入/输出；设计器连线、编译器和运行时都消费同一契约，删除前端独立硬编码矩阵。
- **验收标准**：开始→LLM→审批/结束以及 HTTP→LLM→条件路由可正常连线、发布、执行；非法端口组合在设计时与发布时均被拒绝。
- **依赖**：COR-001。

#### LLM-003（P1）LLM 缺少生产治理

- **现状证据**：已有真实调用入口和节点输出持久化，但缺少完整的结构化输出校验、模型白名单、预算、重试边界、敏感信息脱敏、Prompt 注入防护和人工复核策略。
- **风险**：非确定输出直接驱动关键审批，成本失控，输入或日志泄露敏感信息，模型失败难以恢复。
- **改造方案**：节点必须可配置 JSON Schema、超时、最大 Token、温度、模型白名单、单次/单流程预算和失败分支；对输入字段做分类与脱敏；外部知识/工具输出视为不可信；关键动作必须经过确定性校验或人工闸门。
- **验收标准**：Schema 不合法进入失败分支；预算超限不再调用；敏感字段不出现在日志；重试使用同一幂等上下文；模型不可用时流程可按配置人工接管。
- **依赖**：LLM-001、COR-003、AUD-001。

#### HTTP-001（P1）SSRF 防护仍有 DNS 重绑定窗口

- **现状证据**：[`server/workflow-engine.ts`](../server/workflow-engine.ts#L80) 已限制协议、DNS 解析结果、私网地址、端口、重定向、响应大小和超时，这是重要的安全基础；但预解析后普通 Fetch 仍可能再次解析目标域名。
- **风险**：攻击者可能在两次解析之间切换地址，将请求导向内网或元数据服务。
- **改造方案**：使用固定解析结果的自定义 Dispatcher/连接器，或统一走受控 Egress Proxy；每次重定向重新验证并固定目标；生产环境再叠加出站网络策略。
- **验收标准**：DNS rebinding、IPv4/IPv6 混合、十进制/八进制 IP、重定向到私网、端口绕过等用例全部被阻止。
- **依赖**：无。

#### HTTP-002（P1）HTTP 节点缺少凭据、可靠性和幂等治理

- **现状证据**：没有完整的 Secret 引用、域名白名单、重试/退避、熔断、幂等键和调用关联 ID。
- **风险**：密钥可能进入定义；重试造成重复付款/写入；外部服务故障拖垮 Worker。
- **改造方案**：定义 `SecretRef`，运行时按权限注入；区分安全可重试与不可重试请求；支持退避、熔断、并发限制和调用幂等键；记录脱敏请求摘要与外部关联 ID。
- **验收标准**：定义导出不含密钥；401/429/5xx/超时按策略处理；POST 重试必须带幂等键；熔断与恢复可观测。
- **依赖**：COR-003、IAM-001。

#### DATA-001（P1）数据源“已验证”状态不可信

- **现状证据**：[`server/p2-service.ts`](../server/p2-service.ts#L74) 创建数据源时可直接写入 verified 和 `lastTestedAt=NOW()`，没有执行真实连接测试。
- **风险**：用户会把配置保存成功误认为网络、凭据、权限和 Schema 已验证，直到运行时才失败。
- **改造方案**：创建状态默认为 `untested`；单独的连接测试 Job 使用 SecretRef 执行最小只读探测，保存测试目标、时间、延迟、结果码和脱敏错误；配置变化后自动失效旧验证。
- **验收标准**：错误主机、错误凭据、无权限、超时和成功连接得到不同结果；未经测试的数据源不能标记 verified。
- **依赖**：Secret 管理、COR-003。

#### DATA-002（P1）数据流是样例执行器而非真实 ETL

- **现状证据**：[`server/p2-service.ts`](../server/p2-service.ts#L200) 主要读取 `sampleJson` 或返回 `validated_read_plan`/`metadata_safe`；共享节点契约允许更多节点，但执行器会拒绝不支持类型。
- **风险**：设计器展示的能力与运行时不一致，无法处理真实数据、批次失败、断点续跑和资源隔离。
- **改造方案**：若短期不建设，给数据流加实验性 Feature Flag 并在 UI 明示；若建设，则拆分 Connector、只读查询规划、UDF 沙箱、批次 Worker、Checkpoint、血缘和结果存储。所有节点仍由同一能力注册表驱动。
- **验收标准**：至少一个真实只读数据库连接器完成 Schema 发现、参数化查询、分页、超时和断点续跑；UDF 受 CPU/内存/时长/网络限制；前后端支持矩阵完全一致。
- **依赖**：DATA-001、COR-003。

#### FRM-001（P1）表单节点缺少权威运行时校验

- **现状证据**：运行时主要返回字段定义与输入，未完整执行必填、类型、条件显示、附件、字段级读写权限和版本兼容校验。
- **风险**：绕过前端即可提交非法值或修改只读字段；后续节点收到不稳定数据结构。
- **改造方案**：把表单 Schema 版本化，服务端使用同一 Schema 做创建、暂存和提交校验；表达式只在受限解释器运行；区分可见、可编辑、必填和脱敏权限。
- **验收标准**：API 直调不能绕过校验；历史运行固定旧 Schema；附件大小/类型/病毒扫描状态可校验；字段变更有兼容性提示。
- **依赖**：IAM-001。

#### SUB-001（P1）子流程设计契约与运行时不一致

- **现状证据**：共享契约暴露挂起、发送/接收、入口/出口等配置，而运行时主要使用 `subflowId` 与输入，且嵌套/操作节点受到额外限制。
- **风险**：用户保存了看似有效的配置，执行时却被忽略或失败。
- **改造方案**：明确同步等待、异步启动和调用活动三种模式；固定被调用版本；实现输入/输出映射、状态传播、取消传播、递归深度和权限边界。未实现配置从 UI 和 Schema 删除或标注实验性。
- **验收标准**：父子流程的成功、失败、取消、超时和输出映射均有集成测试；父流程日志可跳转到子运行，子运行保留独立审计。
- **依赖**：COR-001、COR-003。

### 6.5 治理、安全、运维、审计和指标

#### GOV-001（P0）流程删除会破坏历史证据

- **现状证据**：[`server/workflow-service.ts`](../server/workflow-service.ts#L303) 删除流程时会级联删除告警、任务、参与状态、节点运行、运行、版本、成员和流程，没有活动运行保护。
- **风险**：误操作不可恢复，审批和运行证据丢失，不满足审计与追责要求。
- **改造方案**：默认只允许归档；归档后禁止新运行但保留历史。物理清理由独立保留策略作业执行，要求无活动运行、双重授权、备份点和清理清单；审计事件不得随业务对象删除。
- **验收标准**：普通管理员只能归档；活动运行流程不能清理；恢复归档后历史可读；物理清理需要二人审批并能从备份恢复抽样数据。
- **依赖**：AUD-001、备份恢复能力。

#### SEC-001（P0）明文 HTTP 不满足登录系统安全底线

- **现状证据**：当前检查实例通过 `http://` 访问；登录凭据与会话 Cookie 无法获得 TLS 链路保护。
- **风险**：同网络路径上的攻击者可能窃听或篡改凭据、会话与审批数据。
- **改造方案**：由受控反向代理终止 TLS，HTTP 强制跳转 HTTPS；Cookie 设置 `Secure`、`HttpOnly`、合理 `SameSite`；配置 HSTS；内部代理链正确传递并校验协议头。
- **验收标准**：公网/内网用户入口只允许 HTTPS；HTTP 301/308 到 HTTPS；Cookie 属性自动化检查通过；弱协议/弱密码套件关闭。
- **依赖**：部署域名与证书。

#### SEC-002（P0）应用层安全基线不完整

- **现状证据**：[`server/_core/index.ts`](../server/_core/index.ts#L34) 全局 JSON/URL 编码请求体上限为 50 MB，健康接口仅返回 `{ok:true}`；未形成统一安全头、登录限流/锁定、来源策略、请求 ID 和结构化安全日志。
- **风险**：暴力登录、资源消耗、跨站请求、问题追踪困难；过大通用请求体扩大攻击面。
- **改造方案**：按路由设置最小请求体上限；增加 Helmet/CSP、严格 CORS/Origin、状态变更请求的 CSRF 设计、登录 IP+账号双维限流与渐进锁定；所有请求生成 `requestId`，敏感操作记录安全事件。后续补充 MFA、密码重置和会话设备管理。
- **验收标准**：暴力登录、跨来源写请求、超大载荷被拒绝；错误不泄露栈/SQL；同一请求可从 API 日志关联到审计与节点运行。
- **依赖**：AUD-001。

#### OPS-001（P1，核心部署按 P0 门禁）就绪检查不足

- **现状证据**：`/healthz` 只能证明 Node 进程响应，不能证明数据库可写、迁移版本正确、Worker 可领取任务或已启用的 LLM Provider 可用。
- **风险**：负载均衡把请求发送给尚未就绪或已经失去关键依赖的实例。
- **改造方案**：区分 `/livez` 与 `/readyz`；就绪检查数据库、迁移版本、Worker 心跳、队列滞留和被声明为必需的 Provider；返回构建 SHA、启动时间和能力状态，但不泄露密钥。
- **验收标准**：数据库断开、迁移落后、Worker 停止时 readyz 失败；纯可选 LLM 不阻断核心就绪但明确显示 degraded；部署平台据此摘除实例。
- **依赖**：COR-003、LLM-001。

#### OPS-002（P1）迁移、HA 与恢复流程未形成门禁

- **现状证据**：Docker 启动路径内执行迁移；未体现独立迁移 Job、并发实例竞争控制、数据库回滚兼容窗和定期恢复演练。
- **风险**：多实例同时迁移、失败版本带着半完成 Schema 启动，备份存在但不可恢复。
- **改造方案**：将迁移作为部署前单实例 Job，使用数据库锁和版本检查；采用向前兼容的 expand/migrate/contract；发布前备份，定期恢复到隔离库并运行一致性检查。
- **验收标准**：两个实例并发部署仅一个执行迁移；迁移失败不切流；完成一次从备份恢复并核对流程、版本、运行、任务和审计记录。
- **依赖**：REL-001。

#### AUD-001（P1）审计事件缺少业务语义与不可变性

- **现状证据**：当前大量授权/业务变更使用通用 `user_updated`，目标对象、动作类型、前后值、IP、User-Agent 和请求关联不足。
- **风险**：无法回答“谁因为什么权限对哪个流程/任务做了什么”，也难以调查越权和错误审批。
- **改造方案**：建立类型化事件目录，如 `workflow.published`、`task.delegated`、`approval.rejected`、`permission.denied`；记录 actor、effectiveSubject、resource、before/after 摘要、reason、requestId、IP/UA、时间和结果。审计表追加写，限制修改/删除，并支持受控导出。
- **验收标准**：关键业务动作 100% 有事件；前后值敏感字段脱敏；审计员只读；篡改尝试被拒绝并告警；一次审批可串联 API、任务、运行和节点事件。
- **依赖**：统一请求 ID。

#### OBS-001（P1）运行指标口径不可用于性能治理

- **现状证据**：运行平均时长使用整体起止时间，人工审批等待也被计入；当前实例曾显示约 2,326,041 ms 的平均时长，更接近人工等待而非引擎耗时。
- **风险**：无法区分系统慢、外部依赖慢和人员慢，优化方向与 SLA 告警会失真。
- **改造方案**：拆分 wall time、engine active time、queue time、human wait time、external wait time；提供 P50/P95/P99、队列年龄、任务超期、失败率和重试率，按流程版本和节点类型聚合。
- **验收标准**：一个包含人工等待的运行可准确分解各阶段；仪表盘口径有公式、单位、时区和数据源说明；告警使用窗口和最小样本数。
- **依赖**：COR-003。

#### REL-001（P0）缺少“同一版本”发布与验收证据

- **现状证据**：当前部署 JS 资源哈希与本地当前构建不同；页面没有明确展示 Git SHA/镜像 Digest，无法证明浏览器验收对应当前提交。
- **风险**：代码测试、部署健康和浏览器验收可能来自三个不同版本，造成“已修复/已验收”的假结论。
- **改造方案**：构建时注入 Git SHA、构建时间和版本；服务端 `/version`、页面诊断区、镜像标签统一展示；验收记录必须保存 URL、SHA、镜像 Digest、数据库迁移版本和时间。
- **验收标准**：CI 产物不可变；部署后五处版本信息一致；浏览器 E2E 首步断言目标 SHA，不一致立即失败。
- **依赖**：无。

#### TST-001（P1）测试通过不等于真实依赖已验收

- **现状证据**：当前有 100 项测试通过、25 项跳过；被跳过部分涉及数据库、OAuth、LLM。[`server/workflow-ui-regression.test.ts`](../server/workflow-ui-regression.test.ts#L1) 等测试主要检查源码字符串，不能证明控件可点击或布局可用。
- **风险**：关键路径在本地呈绿色，但数据库事务、并发锁、真实模型、真实浏览器仍未验证。
- **改造方案**：测试分层并分别报告：纯单元、MySQL 集成、API 多身份权限、Worker 崩溃恢复、真实 Provider、组件交互、浏览器 E2E、安全扫描和部署恢复。生产门禁不允许“必需能力”的测试被 skip。
- **验收标准**：报告显示每层执行数、跳过原因、环境和版本；核心发布路径无未解释 skip；浏览器用真实网络/API，不使用源码字符串断言代替行为。
- **依赖**：REL-001。

### 6.6 前端布局、交互、性能和可访问性

#### UI-001（P0）375px 设计器存在页面级横向溢出

- **现状证据**：当前部署在 375px 视口下，页面内容宽约 360px、页面滚动宽约 608px；成员授权表单固定两列是主要来源，节点面板和画布操作区也显著超宽。[`client/src/pages/Home.tsx`](../client/src/pages/Home.tsx#L390) 使用固定 `grid-cols-2` 而缺少窄屏回退。
- **风险**：关键字段、提交按钮或画布动作离开视口，移动端用户可能误填、漏填或无法完成操作。
- **改造方案**：所有表单默认单列，从 `md` 起再多列；外层设置 `min-width: 0`；操作栏在窄屏折行或收进菜单；表格与画布只允许组件内部滚动，禁止扩张页面根宽度。
- **验收标准**：320/375/390/768px 下 `document.documentElement.scrollWidth <= clientWidth`；所有必填字段和主操作无需页面横向滚动；软键盘打开后仍可提交。
- **依赖**：无。

#### UI-002（P1）设计器信息架构过载

- **现状证据**：单页同时承载授权成员、运行参数、画布、治理、详情、运行记录和版本列表，桌面页面高度约 2,600px，用户需要频繁长距离滚动。
- **风险**：主任务“设计与发布流程”被次要信息打断，用户难以判断当前编辑对象、保存状态和发布状态。
- **改造方案**：流程详情按一级任务拆分为“设计”“配置与权限”“运行与监控”“版本与发布”；设计页采用顶部状态栏 + 左节点库 + 中画布 + 右属性面板；保存/校验/发布固定在可见区域。运行参数放到独立启动抽屉。
- **验收标准**：用户在不离开设计视口的情况下完成加节点、配置、校验、保存、发布；切 Tab 保留选择和未保存提示；浏览器前进/后退可恢复子页。
- **依赖**：组件拆分。

#### UI-003（P1）表格、节点库和触控操作不友好

- **现状证据**：流程表格最小宽度约 1,500px，操作列可能离开视口；节点库横向内容宽约 1,400px；多处按钮/图标点击区域约 26–36px。
- **风险**：小屏难以发现操作，触控误点率高，超宽表格让权限和状态信息脱离上下文。
- **改造方案**：桌面表格固定/粘性操作列，窄屏改摘要卡片；节点库按类别折叠、搜索和最近使用；核心触控目标不小于 44×44px，密集桌面工具可保持视觉小但扩大 hit area；危险操作与普通操作分组。
- **验收标准**：375px 下无需横向滚动即可找到查看/编辑/运行主操作；触控目标自动化扫描和人工抽查通过；键盘可操作菜单、画布节点和弹窗。
- **依赖**：UI-002。

#### PERF-001（P2）前端包和页面组件过大

- **现状证据**：生产构建主 JS 约 1.126 MB（gzip 约 299 KB），超过 Vite 500 KB 提示；`Home.tsx`、`WorkflowCanvas.tsx`、`OrganizationManagementPage.tsx`、`ProcessWorkbench.tsx` 均为大型组件。
- **风险**：首屏解析与交互延迟增加，修改影响面扩大，测试困难。
- **改造方案**：按工作区和路由动态导入；画布、组织、IAM、监控独立 chunk；抽离查询 hooks、状态机、属性面板和表格；对图表/编辑器等重依赖按需加载。
- **验收标准**：核心列表首屏不加载画布和组织模块；设置明确 bundle budget，并在 CI 超限失败；慢速设备上记录可交互时间基线。
- **依赖**：UI-002。

#### A11Y-001（P2）可访问性基线不足

- **现状证据**：[`client/index.html`](../client/index.html#L2) 使用 `lang="en"`，视口设置包含 `maximum-scale=1`；尚无完整键盘、焦点、读屏、对比度和缩放验收。
- **风险**：中文读屏发音不正确，用户无法缩放，键盘和低视力用户难以操作复杂画布。
- **改造方案**：改为 `lang="zh-CN"`，允许用户缩放；为图标按钮提供可访问名称；实现可见焦点、跳转主内容、弹窗焦点圈、错误摘要、画布键盘替代操作，并以 WCAG 2.2 AA 为目标。
- **验收标准**：200% 缩放不丢功能；仅键盘可完成登录、启动、审批和发布；自动扫描无严重问题，关键页面通过读屏抽查。
- **依赖**：UI-002、UI-003。

#### ORG-001（P2）同名组织缺少消歧信息

- **现状证据**：组织树和人员选择中可出现相同显示名，如多个“管理部”或“研发组”，但部分位置没有显示完整组织路径/编码。
- **风险**：审批候选、成员授权和审计查询可能选错组织。
- **改造方案**：选择器与审计记录统一显示“公司 / 部门 / 子部门（编码）”；树节点可保持短名，但悬浮和搜索结果显示完整路径。
- **验收标准**：同名组织在搜索、候选人预览、任务详情和审计中均可唯一识别。
- **依赖**：组织树路径查询。

#### DOC-001（P2）验收文档存在状态冲突

- **现状证据**：历史 `todo.md` 曾记录 375px 无溢出，而当前部署检查仍发现溢出；完整性清单与节点证据矩阵对部分能力的“完成/缺失”结论也不一致。
- **风险**：团队无法知道哪个结论是当前有效基线，旧勾选项会掩盖回归。
- **改造方案**：本文作为新改造入口；每项 Todo 只能由带版本、环境、证据链接的验收记录关闭。历史文档保留但加“适用提交/已被替代”说明，不删除证据。
- **验收标准**：所有完成项均能追溯到提交、测试层和浏览器/运行证据；相互冲突的文档有明确 superseded 关系。
- **依赖**：REL-001。

## 7. 推荐目标架构

```text
设计器
  -> 节点能力注册表（前后端共享 Schema/端口/配置）
  -> WorkflowCompiler（静态校验、规范化、执行计划、版本哈希）
  -> 发布版本（不可变）

API Command 层
  -> 授权与职责分离
  -> 幂等命令/Outbox
  -> 数据库事务

Scheduler / Worker
  -> 租约领取与续租
  -> Run Token / Node Instance / Attempt
  -> Timer / Retry / Compensation
  -> HTTP、LLM、Data 等受控执行适配器

Human Task 服务
  -> ParticipantResolver
  -> Assignment Snapshot / Delegation
  -> ApprovalDecision / Sign Policy
  -> SLA / Escalation

统一治理
  -> Secret Manager
  -> IAM Policy Engine
  -> Append-only Audit
  -> Metrics / Trace / Alert
  -> Archive / Retention / Backup Restore
```

### 7.1 必须坚持的设计原则

1. **定义与运行分离**：运行固定引用已发布、不可变版本，草稿变化不影响在途实例。
2. **前后端单一能力真源**：节点是否可连接、可配置、可执行不能分别硬编码。
3. **状态迁移持久化**：关键状态与下一步 Job 同事务写入，不以进程内数组/Set 作为权威状态。
4. **所有外部副作用幂等**：HTTP、LLM 工具、子流程和通知都有业务幂等键与尝试记录。
5. **权限在服务端执行**：按钮隐藏不是安全边界，运行命令和任务决定均重新授权。
6. **失败可解释、可恢复**：不静默跳过节点、不把死路标为成功，不依赖人工改库恢复。
7. **能力真实标识**：没有部署依赖或尚为样例的节点应禁用/标实验性，不能显示成可用。

## 8. 分阶段改造路线

### M0：冻结基线与验收体系

目标：先让“哪个版本、哪层验证、什么算完成”可证明。

- 注入构建 SHA、镜像 Digest 和迁移版本；
- 建立测试分层报告和必须能力不得 skip 的规则；
- 建立节点能力清单，标记 production/beta/experimental/disabled；
- 修正文档 superseded 关系，保留历史证据；
- 为 P0 场景准备数据库、并发、重启和浏览器验收夹具。

### M1：生产正确性的最小内核

目标：任何流程都不会错误成功、丢任务、错误审批或破坏历史。

- WorkflowCompiler 与终点成功条件；
- ApprovalDecision 和真实拒绝路径；
- 或签/会签按决定计票；
- 持久化 Worker、租约、幂等、重启恢复；
- 归档替代硬删除；
- HTTPS、登录防护、readyz；
- 修复 375px 页面级溢出。

### M2：人工流程业务完整性

目标：覆盖组织型审批、人员变更、在途运维和职责分离。

- ParticipantResolver 扩展；
- 加签/转办/委托/改派；
- 暂停/恢复/取消/定时器/SLA；
- 表单权威校验与子流程契约；
- 细粒度 IAM、职责分离、类型化审计；
- 重新组织设计器信息架构与运行指标。

### M3：外部集成与智能节点生产化

目标：让 LLM、HTTP 和数据节点成为受控、可恢复、可观测的真实能力。

- Provider 与 Secret 管理；
- LLM 连线、结构化输出、预算与安全；
- HTTP 固定 DNS、白名单、重试/熔断/幂等；
- 真实数据源测试、Connector、只读 SQL、UDF 沙箱和 Checkpoint；
- 真实依赖 E2E 与故障注入。

### M4：体验、性能与治理完善

目标：降低使用成本并建立长期演进门禁。

- 路由拆包与 bundle budget；
- 触控、键盘、读屏、缩放验收；
- 同名组织消歧；
- 指标仪表盘、容量基线、备份恢复演练和保留策略自动化。

## 11. 生产发布 Definition of Done

一个改造项只有同时满足以下条件才能勾选完成：

1. 需求、状态机、权限和失败行为有明确契约，不依赖口头约定。
2. 数据迁移可向前执行，存在备份/恢复或回滚策略。
3. 服务端是权威校验边界，不能通过直调 API 绕过前端限制。
4. 单元、真实数据库、权限、并发/恢复测试按风险执行且无未解释跳过。
5. 涉及 UI 的能力通过桌面和 375px 真实浏览器业务闭环；涉及触控的能力同时检查 320/390px。
6. 涉及 LLM、HTTP、数据源的能力使用真实依赖完成成功与失败路径，不以 Mock 作为最终验收。
7. 日志、指标和审计足以回答失败原因、当前责任人、重试历史和最终结果。
8. 验收记录包含 Git SHA、镜像 Digest、迁移版本、环境、时间和证据链接。
9. 文档和能力状态同步更新；未完成能力必须关闭入口或明确标记实验性。
