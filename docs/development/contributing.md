# 提交、评审与发布约束

## 划定本次变更

从明确的用户目标或问题编号开始。一次提交通常对应一项可独立验证、可说明回滚影响的改动。需要一起上线的接口、迁移、调用者和验收用例放在同一评审范围。保留已有作者的工作区改动。需要新分支时可使用 `codex/<主题>`，已有任务分支沿用其约定。

在 Windows 11 的 PowerShell、仓库根目录确认起点和差异。

```powershell
git status --short --branch
git rev-parse HEAD
git diff --stat
git diff --cached --name-status
```

提交说明使用中文，首行描述对象与行为，例如 `修复业务导入在纠正失败行后无法续传的问题`。正文说明触发现象、修改范围、兼容性、执行过的测试、失败及外部依赖。单纯的“优化”“修复若干问题”不足以定位行为。

## 暂存与评审

逐个暂存本次明确涉及的文件。下面用新增项目指引举例，实际操作时将路径替换为自己的文件。执行提交、推送和部署各按当前授权范围进行。

```powershell
git add -- Agent.md AGENTS.md
git diff --cached --name-status
git diff --cached --check
git diff --cached --stat
git status --short --branch
```

| 评审项 | 随变更提供的事实 |
| --- | --- |
| 用户结果 | 谁从哪个入口做什么，变更前后看到什么，如何回读真实结果 |
| 兼容性 | 旧流程或历史实例、旧客户端或 Worker、迁移和回滚的读写关系 |
| 权限与并发 | 权限在哪个事务核对，两个请求竞争或回执中断后得到什么 |
| 测试 | 命令、被测提交、隔离环境、结果数、失败用例、生产级验收仍缺什么 |
| 可追溯性 | 关联需求/评审编号，涉及公共行为时同步索引、用例或发布记录 |

仅暂存可评审源码、迁移、测试与长期文档。经核对的合成数据截图可随 README 或使用说明发布。口令、部署私钥、Cookie、浏览器登录态、真实业务导出、原始验收截图和运行日志留在对应私有存储。若历史提交中发现凭据，单独处理轮换、会话撤销和历史影响。删除当前文件中的字面值仅完成代码侧整改。格式化按改动文件选择，避免全仓格式化掩盖业务差异。

## 发版与恢复

GitHub 对 `main` 要求 `Application regression` 成功并禁止强推和删除。向 `main` 交付前，先在候选提交上取得成功结果，并核对检查对应的提交 SHA。需要修复失败时将改动提交到候选分支，使用新提交重新验收。[主应用检查定义](../../.github/workflows/ci.yml)

1. 记录待发布的 Git 提交、源码指纹、迁移版本、构建预算及测试结果。并行开发时核对工作树、远程分支和当前运行镜像的身份。
2. 按[部署说明](../deployment-linux-docker.md)核对备份、镜像摘要、配置来源和数据库兼容性。验收账号、目标业务及外部调用费用需与本次环境匹配。
3. 切换后核对健康探针、就绪、静态资源和实际构建身份，再跑一条带回读的业务链。公共 `/version` 显示产品版本。部署身份另取镜像或服务端诊断。
4. 失败时记录阶段、运行中的镜像和迁移状态。可直接回滚且获授权时切回已验证镜像，重新核对就绪与业务样本。需要恢复数据库时按约定的恢复点、备份和授权范围处理。提交、推送、构建、上线、验收分别记录结果。

在 `codex/release/**` 候选分支推送后，[发布包构建](../../.github/workflows/release-candidate.yml)生成 Linux amd64 镜像、源码、`SHA256SUMS` 和 `release-manifest.json`。远程验收使用该候选制品。待 `main` 指向同一提交并完成回归，再将同一制品和验收摘要上传至 GitHub Release。
