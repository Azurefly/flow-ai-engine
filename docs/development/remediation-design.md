# 功能整改与缺失模块设计

本设计基于 2026-11-19 的业务验收。F 编号对应已观察的问题或可追溯性缺口，G 编号对应候选能力。P0 优先处理凭据暴露，P1 先解决发布及数据正确性，P2 改进可维护性或使用体验。新增服务和表名均为设计建议，排期前由对应模块负责人确认。[评审基线](review-baseline.md)

## 首批整改保护部署与验收结果

| 编号与负责人 | 修改方案 | 完成条件 |
| --- | --- | --- |
| F01 / P0，维护者与运维 | 移除四个历史 E2E 脚本中的管理员口令回退。核对该配置对应的账号、历史提交和分发范围。对实际使用过的凭据轮换并撤销相关会话。统一从环境注入短期测试身份，记录指纹或配置项名称即可。 | 在没有测试目标或身份配置的环境运行，脚本在第一次网络请求前退出。检查工作树及发布物，另由账号所有者确认轮换和撤销结果。 |
| F02 / P1，部署负责人 | 给实际对外入口配置证书与 TLS 终止，明确受信代理、Cookie 的 Secure 判定、内部探针和前端基准 URL。将现有公网 HTTP 入口收敛到 HTTPS 重定向或限制为内部访问。 | 在受支持的外部入口通过浏览器验证登录、刷新、退出。原 HTTP 地址无法提交明文登录。保留既有可信管理通道直至验证完成。 |
| F06 / P1，执行器与测试维护者 | 保留对业务出口和作业唯一性的断言。按本次实例的恢复作业 ID，在有界时限内等待终态，再验作业数量及结果。记录 `run.status`、`job.status` 和读取时间。 | 同一专用 MySQL 上重复执行签署用例，或签与比例会签都经过原业务断言。在 Worker 崩溃恢复场景仍能识别重复续跑或长期租约。 |
| F07 / P1，验收脚本维护者 | 路由脚本取所读定义版本和审核状态，广播夹具绑定分发/汇聚双方。质量用例在实际拒绝阶段断言非法阈值，并核对无残留。指标用例自建可终止实例，回读样本数。历史脚本逐个统一显式目标与专用命名空间。 | 从空的隔离库重复运行这三组脚本。每次使用本次创建的 ID。缺少目标时拒绝运行，失效权限和版本冲突仍被业务接口拒绝。 |
| F08 / P2，模型节点维护者 | 在节点运行元数据中分别保存请求模型、供应商返回模型和配置修订，必要时保存供应商请求编号。历史记录缺失时显示“当时未记录”。 | 用返回别名的受控供应商用例核对两种模型名，并保留一次真实流程记录。平台不根据模型名差异自动判定供应商选错模型。 |

## F03、F04 / P1　业务 CSV 导入

**用户结果。** 管理员上传一份业务清单，能在写入前看到每个错误的位置。提交后断线、超长或重复时，能准确知道哪些记录已经创建，以及如何继续。现有实现逐物理行解析并由浏览器依次创建项目，后续记录出错会留下已成功的行。[业务中心](../../client/src/components/ProjectWorkspace.tsx)

**接口与数据。** 建议将解析和业务校验归入共享或服务端实现。按完整输入解析 UTF-8/BOM、逗号、转义双引号、引号内 CRLF、末尾空行及闭引号。保留逻辑记录号、物理起始行、字段、原值摘要和诊断码。`project.previewImport` 接受文件、大小限制和模板版本，返回批次标识、摘要、逐行问题和预计变更，预检阶段的业务写入为零。沿用现有项目创建、默认授权和审计服务。

**执行与恢复。** 建议增加 `project_import_batch` 和 `project_import_row`，批次保存发起人、文件摘要、修订与状态。行保存稳定行号、业务代号、规范化内容摘要、结果和创建对象 ID。`project.commitImport` 接受所读批次修订和请求键，`project.importStatus` 返回成功、失败与待处理行。先完成整批静态预检，再以每行短事务执行并登记回执。并发创建造成的真实冲突标到该行。同一批次已成功的同一内容可直接核对。相同代号对应其他已有项目时要求用户显式处理。可编辑失败行后仅续传剩余项。

**界面、交付和退回。** 第一阶段交付语法解析、行级错误和完整预检。第二阶段交付持久批次及断线恢复。导入结果在本业务页保留，可下载错误行。关闭全局提示不会丢失批次。旧的手工新增仍可用，停用新入口后已提交批次应可查。验收用 CSV-01/02，增加空文件、重复表头、同码异内容、两个客户端竞争及权限撤销。[用例卡](test-case-template.md)

## F05 / P1　手动数据运行的请求核对

**现状与影响。** 本轮用正式 `data.run` 向同一测试流程提交同一输入，客户端丢弃首次回执后重试，两个 `manual` 实例均成功。当前请求未提供客户端可重复使用的操作键，定时任务有自己单独的时间桶。请求结果未知时，即使 UI 禁用双击，重新打开页面的用户也无法可靠辨认原实例。[数据服务](../../server/p2-service.ts)

**命令合同。** 建议新增兼容字段 `idempotencyKey`、`expectedDefinitionVersion`，使用项目、流程、运行主体和触发模式限定请求键作用域。服务端生成规范化输入及执行版本摘要。首次提交在同一事务创建请求回执、运行与作业。同键同内容返回原 `runId`，同键异内容返回冲突，新的一次主动发起生成新键。旧客户端沿用现有合同，迁移后的 UI 从点击发起起保留该请求键。

**查询与权限。** 建议提供 `data.runReceipt`，仅向当前有权的调用者返回对应运行 ID 和最少状态。回执和业务运行一并保留到明确的保留期限。区分已知拒绝、网络结果未知、已入队、执行失败和取消。重新发起与重试界面使用不同动作。失败执行复跑由新请求关联原运行。

**验证与退回。** 依次覆盖同时发两份请求、首次响应丢失、等待期间撤权、相同键不同输入、部署升级后查旧实例、用户明确运行第二次。观察运行表和作业表各新增几条。迁移先加可选字段及唯一约束，再启用新客户端。回退客户端后继续提供既有回执查询。[DATA-01](test-case-template.md)

## G01　可执行数据源与受控输出

**需求与边界。** 当前内联样本和受支持的 MySQL 只读查询可执行。API 能测试连通性，文件能登记，两者的实际读取都被运行预检正确阻止。现有 sink 的可执行模式为 `audit_only`。需要用真实接口、定期文件或下游入库的客户，应将这些能力作为单独需求排期。[数据源能力](../../shared/data-source-capabilities.ts) · [执行器](../../server/p2-service.ts)

- **合同。** 以数据源种类、协议、支持操作、凭据引用、资源版本及状态公开能力。让登记页、节点选择、预检、发布和 Worker 使用同一判定。读、预览和写的授权分开，项目级凭据引用沿用现有受管端点机制。
- **API 与文件读取。** 首批选一个有稳定分页的只读 API 及 UTF-8 CSV 文件。API 配置游标、字段映射、页/行/字节/超时边界。文件先上传到授权对象存储，记录对象版本、内容摘要、大小、格式及清理期限，锁定上传版本后再运行。解析错误定位逻辑行和字段。
- **运行与恢复。** 作业记下实例、节点执行键、输入资源版本、最近已提交页或文件位置和产物摘要。按页写入临时产物与检查点，完成后切换可读清单。读取失败保留计数和最后成功位置，取消后停止派发新页，记录连接实际释放时间。
- **对外写入。** 读取能力验证后，再接一种有幂等回执的目标，支持 dry-run、行级校验与写前审批。用实例、节点执行轮次和行键防重复，保留回执。结果不确定时先查目标状态。明确只审计、预览、真正外部提交三种结果。
- **验收与回退。** 合成分页端点中途超时、文件版本替换、中文多行、同页重试、用户撤权、取消与断点恢复均有用例。真实客户连接单独验收。按连接器能力开关分批上线。撤回后保留旧实例的证据及只读查看。

## G02　能等待人工或消息的子流程

当前私有同步子流程有定义快照。嵌套定义创建会被拒绝，人工和等待节点有明确诊断。跨部门可复用审批、可暂停或需等待外部回执的子流程，是这套同步模型尚未覆盖的需求。[子流程诊断](../../server/subflow-diagnostics.ts)

| 决策 | 建议设计 |
| --- | --- |
| 身份与版本 | 调用节点显式选择同步或异步。发布父流程时固定子定义及版本/摘要，按项目与调用权限校验。编译时查环，限制深度和并发扇出。 |
| 持久关系 | 新增 `workflow_run_link`，按父实例、父节点执行轮次、子调用序号唯一绑定子实例。记录父子快照、入参与结果映射、状态和取消策略。 |
| 推进 | 同一事务创建父等待事实、子实例与子作业。子流程终态写事件，父恢复操作按关联键只处理一次。重启、重复回调、多个子完成次序变化都能回读。 |
| 失败与人工 | 失败回传结构化错误，父节点配置终止、人工处理或重试。父取消时只向未结束的关联子实例发送一次取消。任务办理资格在子实例重新判定。 |
| 页面与交付 | 父运行详情可查看子实例链路、实际版本、等待原因及取消传递结果，读取两端分别授权。先交付一层异步人工审批，再开有界嵌套。旧同步流程维持原快照语义。 |
| 验收 | 父暂停期间子完成、父取消与子完成竞争、子实例创建后崩溃、重复回调、循环引用、越权读取和旧父版本重放。每组核对父仅续跑一次。 |

## G03　内部账号、部门和成员关系批量导入

用户确认由系统内部管理账号与组织。本轮以用户名、部门编码及两者组合识别账号、部门与成员。入口位于业务中心导入菜单及人员与权限的组织架构页。

管理员与仅有目录预览权的观察者可上传版本 1 的 UTF-8 JSON 文件。预览保存逐行原镜像；应用按同一批次和行锁复核身份、依赖与版本，在同一事务写入对象、回执和授权审计。初始口令在应用新增账号时单独录入。

缺项保留。新增成员关系默认非主部门；移动既有部门继续使用原组织树流程。回退复核写后镜像，新增且仍未使用的账号及部门可停用，已被另改或使用的对象须由管理员核对。

A59–A62。在隔离 MySQL 验证观察者与应用者、并发、冲突、权限和口令；在远程部署通过系统 API 验证创建、改名、按批重放、逐行回读及回退。
